# Plan: Moodle Web Services Integration Layer

## Context
The current `LmsBridgeService` (`services/lms-bridge.service.js`) uses direct MySQL queries against Moodle/WordPress tables (`kyd4_*`, `sl_*`). This is tightly coupled, fragile, won't work when Moodle is on a separate server, and doesn't scale. The user confirmed Moodle web services work via curl. We need a modular, configurable HTTP-based integration layer.

### Client Features (`client.js`)
- **Token-based auth**: All requests include `wstoken` in POST body
- **Retry strategy**: Exponential backoff (1s, 2s, 4s) configurable
- **Error classification**: Transient vs fatal vs auth vs validation errors
- **Moodle error detection**: Parses `exception` and `errorcode` from JSON responses (Moodle returns HTTP 200 even for WS errors)
- **Logging**: Configurable log levels (`info`, `debug`)
- **Graceful degradation**: Functions fail gracefully when Moodle not configured

## Key Design Decisions

1. **Graceful Degradation**: If `MOODLE_URL` or `MOODLE_WS_TOKEN` is not set, the module disables itself and logs warnings instead of crashing the server
2. **Idempotent Enrolment**: `autoEnrolStudent()` checks if user already exists and if already enrolled before creating/enrolling
3. **Batch Support**: `batchAutoEnrol()` for B2B orders with multiple students
4. **Retry with Backoff**: Transient failures (network, 5xx, 429) are retried with exponential backoff
5. **Audit Logging**: All auto-enrol actions are logged to `order_audit_logs`
6. **Separation of Concerns**: Each service file handles one domain (user, course, enrolment)
7. **Centralized Error Handling**: `MoodleError` class with error codes for different failure modes
8. **No Hard Dependencies**: Services fail gracefully — payment flow continues even if Moodle is down
