# Fix Payment System Database Issues

## Problem Analysis
The payment system is failing due to database column naming mismatches:

1. **PaymentAttempt table column mismatch**: The database table `aggp_payment_attempts` has snake_case column names (e.g., `payment_intent_id`, `provider_id`, `transaction_number`) due to global Sequelize `underscored: true` config, but the PaymentAttempt model was temporarily set to `underscored: false`, causing camelCase column names in SQL queries.

2. **Provider selection issues**: 
   - Maviance provider routes still exist in database despite being commented out in code
   - CinetPay API calls are failing with network errors
   - Kkiapay health checks failing

## Root Cause
The database was created with `underscored: true` globally, creating snake_case columns. When I temporarily set `underscored: false` on the PaymentAttempt model, it generated camelCase column names that don't match the existing database schema.

## Solution Plan

### Phase 1: Fix Database Column Naming
1. **Revert PaymentAttempt model** to use `underscored: true` (global setting)
2. **Update field names** in the model to use snake_case to match database:
   - `paymentIntentId` → `payment_intent_id`
   - `providerId` → `provider_id` 
   - `transactionNumber` → `transaction_number`
   - `requestPayload` → `request_payload`
   - `responsePayload` → `response_payload`
   - `errorCode` → `error_code`
   - `errorMessage` → `error_message`

### Phase 2: Clean Up Provider Routes
1. **Remove Maviance routes** from database since provider is not implemented
2. **Update provider health checks** to handle failures gracefully
3. **Improve CinetPay error handling** to diagnose API failures

### Phase 3: Test and Validate
1. **Test payment initialization** with working providers
2. **Verify database operations** work correctly
3. **Check provider failover** logic

## Implementation Steps
1. Update PaymentAttempt model field definitions
2. Remove Maviance provider routes from database
3. Enhance error logging for provider failures
4. Test payment flows end-to-end

## Risk Assessment
- **Low risk**: Changes are isolated to PaymentAttempt model and provider cleanup
- **Data integrity**: No data loss expected, only schema alignment
- **Backward compatibility**: Changes align model with existing database schema

- Payment initialization succeeds without database errors
- Provider selection works with available providers (CinetPay, Kkiapay)
